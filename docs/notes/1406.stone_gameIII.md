# Stone Game III

## Problem

- **Name:** Stone Game III
- **Number:** 1406
- **Difficulty:** Hard
- **Category:** Dynamic Programming, Game Theory, Minimax

---

## Core Pattern

**Pattern:** Minimax Dynamic Programming (Score Difference DP)

### Recognition Cues

Look for problems where:

- Two players play optimally.
- Each player maximizes their own score.
- Both players have the same available moves.
- You're asked to determine the winner instead of the actual moves.

The key observation is that the game can be modeled by the **score difference** between the current player and the opponent.

---

## Intuition

Instead of tracking Alice's and Bob's scores separately, think only about the **advantage** the current player can obtain.

Suppose the current player takes some stones worth `curr`.

The opponent then starts playing optimally from the next position.

If the opponent can achieve an advantage of `X`, then the current player's final advantage becomes:

```
curr - X
```

This eliminates the need to explicitly model turns.

---

## Brute Force

### Idea

Try all possibilities recursively.

Each player may take 1, 2, or 3 stones.

### Complexity

Time:

```
O(3^n)
```

Space:

```
O(n)
```

### Why Inefficient

The same suffixes are recomputed repeatedly.

---

## Optimal Solution

### Key Observations

- Only the current index determines the remaining game.
- The current player's identity is implicit.
- DP state stores score difference rather than absolute scores.

### State

```
dp[i]
```

Maximum score difference obtainable starting from index `i`.

### Transition

For each legal move:

```
take current stones

advantage =
currentSum - dp[nextIndex]
```

Take the maximum over all legal moves.

---

## Algorithm

1. If no stones remain, return 0.
2. Memoize each index.
3. Try taking 1, 2, and 3 stones.
4. Compute:

```
currentSum - predict(nextIndex)
```

5. Store the maximum value.
6. At the end:
   - Positive → Alice
   - Negative → Bob
   - Zero → Tie

---

## Complexity

Time:

```
O(n)
```

Space:

```
O(n)
```

---

## Edge Cases

- Single stone
- Two stones
- Three stones
- All negative values
- All positive values
- Mixed positive and negative values
- Tie
- Taking fewer than three stones near the end

---

## Alternative Approaches

### Bottom-Up DP

Compute answers from the end toward the beginning.

Pros:
- No recursion.
- Avoids recursion stack.

Complexity remains O(n).

## Python Tips

- Use a running sum while iterating over 1–3 stones.
- Memoize by index only.
- `functools.cache` can replace a dictionary.
- Avoid slicing (`nums[i:i+3]`) inside recursion.

## Personal Takeaways

- In two-player optimal games, think in terms of **score difference**.
- DP state should contain only information that affects future decisions.
- Minimax often becomes a simple subtraction recurrence.
- Legal transitions should be generated explicitly instead of using sentinel values.
