# Cinema Seat Allocation

## Problem

- **Name:** Cinema Seat Allocation
- **Difficulty:** Medium
- **Category:** Greedy / Hash Map / State Compression

## Core Pattern

- **Main algorithmic pattern:** Local state compression with a greedy choice.
- **Recognition cues:** A large input is mostly irrelevant except for a small set of positions; each independent group can be evaluated using a constant number of configurations.
- **Why the pattern applies:** For each occupied row, only seats 2–9 affect whether a four-person family can be placed. There are only three candidate four-seat blocks: 2–5, 4–7, and 6–9.

## Intuition

An experienced engineer should first notice that rows are independent. An empty row always accommodates two families, so only rows appearing in `reservedSeats` need special handling.

For an occupied row, reduce the problem to three possible blocks:

- Left: 2–5
- Middle: 4–7
- Right: 6–9

The left and middle blocks overlap, and the middle and right blocks overlap. The left and right blocks do not overlap, so at most two families can be placed in a row.

The implementation therefore evaluates the three blocks and greedily consumes overlapping alternatives once a block is selected.

## Brute Force

- **Idea:** For every row, enumerate possible arrangements of four-person families and determine the maximum compatible set.
- **Complexity:** Could be expressed as a constant amount of work per row, but iterating through all `n` rows is unnecessary because most rows are empty.
- **Why it is inefficient:** `n` can be very large, while only rows present in `reservedSeats` contain information that needs processing.

## Optimal Solution

### Key observations

1. Empty rows always contribute 2 families.
2. Only rows containing reserved seats need to be examined.
3. Only seats 2–9 matter for family placement.
4. There are only three candidate blocks.
5. The left and right blocks can coexist; the middle block overlaps both.

### Data structures used

- A dictionary mapping each occupied row to its reserved seats.
- Three sets representing the candidate blocks.

### Algorithm explanation

First group reserved seats by row.

Initialize the answer with two families for every row that has no reservation.

For each occupied row, check whether each of the three candidate blocks is completely free. If the left block is available, count it and invalidate the overlapping middle block. If the middle block is available, count it and invalidate the overlapping right block. Finally, count the right block if it remains available.

## Algorithm

1. Create three candidate sets: `{2,3,4,5}`, `{4,5,6,7}`, and `{6,7,8,9}`.
2. Group every reserved seat by row.
3. Add `2 * (n - number_of_occupied_rows)` to the answer.
4. For each occupied row:
   - Assume all three candidate blocks are valid.
   - For every reserved seat in the row, invalidate every candidate block containing that seat.
   - If the left block is valid, add one family and mark the middle block unavailable.
   - If the middle block is valid, add one family and mark the right block unavailable.
   - If the right block is valid, add one family.
5. Return the total.

## Complexity

- **Time Complexity:** `O(R)`, where `R` is the number of reserved seats. Each reserved seat is processed a constant number of times.
- **Space Complexity:** `O(R)` for grouping reserved seats by row.

## Edge Cases

- `reservedSeats` is empty: every row contributes two families.
- All reservations are concentrated in one row.
- Reservations affect only seats 1 and 10: both families can still be placed.
- Reservations block the left and right groups but leave the middle group available.
- Reservations overlap multiple candidate blocks.
- A row can contribute 0, 1, or 2 families, never 3.

## Alternative Approaches

1. **Bitmask per row:** Represent seats 2–9 as bits and test the three candidate masks. This is more compact and can make the state representation explicit.
2. **Direct row-pattern encoding:** Store only the reserved seats from 2–9 and compare against the three required groups.
3. **Set-based implementation:** The submitted solution uses sets for the three candidate blocks and a dictionary for occupied rows. This is simple and readable.

## Python Tips

- Use set literals such as `{2, 3, 4, 5}` instead of `set([2,3,4,5])`.
- `dict` is useful for grouping records by row.
- `set` membership is expected `O(1)` and is appropriate for the candidate blocks.
- When only a few fixed states exist, explicit booleans can be clearer than building a more complicated abstraction.

## Interview Discussion

An interviewer may ask:

- **Why don't you process all `n` rows?**  
  Because empty rows have a known contribution of exactly two families, so only occupied rows need special processing.

- **Why can a row contain at most two families?**  
  The only possible four-seat blocks are the three listed above, and no three of them are mutually compatible.

- **Why can you greedily take the left block before the middle block?**  
  The left block overlaps the middle block, while it does not overlap the right block. When the left block is available, taking it preserves the possibility of taking the right block.

- **Can the solution be reduced to constant space per row?**  
  Yes. A bitmask can encode the relevant reserved seats and eliminate the per-row list representation.

- **Why are seats 1 and 10 irrelevant?**  
  A four-person family never requires either seat.

## Personal Takeaways

1. Separate independent rows before designing the algorithm.
2. Look for a tiny set of valid configurations instead of treating all positions symmetrically.
3. When configurations overlap, identify which combinations can coexist.
4. Precompute the contribution of completely unconstrained parts of the input.
5. State compression can turn a seemingly large seating problem into a constant-size decision per occupied row.
