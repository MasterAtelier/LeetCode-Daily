## Shortest and Lexicographically Smallest Beautiful String

**Problem**

Name: Shortest and Lexicographically Smallest Beautiful String

Difficulty: Medium

Category: Sliding Window / Two Pointers

## Core Pattern

The primary pattern is a variable-size sliding window with a fixed count constraint.

**Recognition cues:**

- Substring/subarray problem.
- Need exactly `k` occurrences of a value (`1` here).
- Optimize the window by length.
- Break ties lexicographically.

The pattern applies because a window containing exactly `k` ones can be maintained with two pointers, and unnecessary leading zeroes can be removed without changing the number of ones.

## Intuition

Maintain a window `[i, j]`.

Expand `j`.

If the window has more than `k` ones, move `i` until it has at most `k` ones.

When it has exactly `k` ones, remove leading zeroes. Those zeroes do not contribute to the required count and therefore cannot be part of the shortest candidate.

Compare the resulting candidate with the best candidate seen so far:

- shorter length wins;
- equal length: lexicographically smaller wins.

The important distinction is between restoring validity and optimizing a valid window.

## Brute Force

Enumerate every substring, count its ones, and keep the shortest valid substring, breaking equal-length ties lexicographically.

Time: O(n^3) in a straightforward implementation if each substring count is recomputed.

Space: O(n) for temporary substring storage.

Prefix sums can reduce the counting work, but the sliding-window solution is simpler and linear in pointer movement.

## Optimal Solution

Use two pointers and maintain `count_1s`.

Key observations:

- `count_1s > k` means the current window is invalid and must shrink.
- `count_1s == k` means the window is valid.
- While the left boundary points to `0`, remove that zero because it cannot help satisfy the `k` ones requirement.

The remaining window is the shortest valid window ending at `j`.

Store only the best window boundaries instead of a deque containing the current window.

## Algorithm

1. Set `i = 0`, `count_1s = 0`, and an invalid answer boundary `end = -1`.
2. For each `j` from left to right:
	- Increment `count_1s` when `s[j] == '1'`.
	- While `count_1s > k`, move `i` right and decrement the count when a `1` leaves.
	- While `count_1s == k` and `s[i] == '0'`, move `i` right.
3. If `count_1s == k`, compare `[i, j]` against the best window.
4. Prefer a shorter candidate.
5. If lengths are equal, prefer the lexicographically smaller substring.
6. If no valid window was found, return `""`; otherwise return the substring represented by the stored boundaries.

## Complexity

Pointer/window processing: O(n).

Exact Python implementation: substring creation/comparison can make the worst-case time O(n^2).

Space: O(n) worst case because substring objects may be created during comparisons.

Given the problem constraint `n <= 100`, this implementation is efficient and appropriate.

## Edge Cases

- No `1`s and `k > 0` -> `""`.
- Exactly one `1` with surrounding zeroes -> `"1"`.
- All characters are `1`.
- The entire string contains exactly `k` ones.
- Multiple candidates have the same minimum length.
- Leading zeroes must be removed before evaluating a candidate.
- The first valid candidate must initialize the answer explicitly.

## Alternative Approaches

- Brute force: simple but unnecessary.
- Deque window: works, but duplicates information already represented by the string boundaries.
- Two pointers with boundaries: preferred because the current candidate is naturally represented by `(i, j)`.

## Python Tips

- Use `s[i:j + 1]` for a candidate when the constraints are small.
- Store indices when the current window is already represented by the source string.
- Check the primary optimization criterion before doing an expensive lexicographical comparison.
- Avoid deque when the only purpose is representing a contiguous substring that already exists in the input string.

## Interview Discussion

Potential follow-ups:

**Why is removing leading zeroes safe?**

Because zeroes do not contribute to the required count of ones.

**Why do we need to compare lexicographically only when lengths are equal?**

Length is the primary optimization criterion.

**Can the current substring be stored without copying it?**

Yes; store its start and end indices.

**Why is the `end == -1` check necessary?**

It distinguishes "no candidate has been found" from a real candidate and correctly initializes the first valid window.

## Personal Takeaways

- Separate validity from optimization in sliding-window problems.
- For exactly `K`, first restore `<= K`, then optimize the valid window.
- Remove leading elements that do not affect the constraint when minimizing a window.
- Store boundaries instead of duplicating the window when the source string already contains it.
- Initialize the first candidate explicitly; an invalid sentinel must not participate in normal length comparison.
