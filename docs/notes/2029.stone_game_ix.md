# Stone Game IX

## Problem

- **Problem:** 2029. Stone Game IX
- **Difficulty:** Medium
- **Category:** Game Theory, Greedy, Counting, Modular Arithmetic

## Core Pattern

### Main algorithmic pattern

**Game-state reduction using counts modulo 3.**

The actual stone values do not matter individually. Only `stone % 3` matters because the losing condition is determined by whether the running sum becomes divisible by 3.

### Recognition cues

Look for:

- A two-player game where the winner depends on a running sum.
- The important condition is divisibility by a small modulus.
- The input can be compressed into counts of residue classes.
- Players choose elements alternately and the order of equivalent residue classes does not matter.

### Why the pattern applies

Every stone belongs to exactly one of three residue classes:

- `0 mod 3`
- `1 mod 3`
- `2 mod 3`

Adding a residue-0 stone does not change the current sum modulo 3, while residue-1 and residue-2 stones move the state between the three possible remainders.

Therefore, the entire game can be represented by the three counts rather than the original array.

## Intuition

An experienced problem solver should immediately ask:

> "What information about a stone actually affects the game?"

Only its remainder modulo 3 affects whether the cumulative sum becomes divisible by 3.

Let:

- `c0` = number of stones congruent to 0 modulo 3
- `c1` = number of stones congruent to 1 modulo 3
- `c2` = number of stones congruent to 2 modulo 3

The key observation is how the `0 mod 3` stones behave.

If `c0` is even, Alice can effectively pair the zero-residue stones so that their influence on the turn structure balances out. In this case, Alice wins exactly when both non-zero residue classes are available.

If `c0` is odd, the zero-residue stones create a turn imbalance. Alice wins only when the two non-zero residue counts differ by more than 2.

This gives the compact condition used by the submitted solution:

- `c0` even → `c1 > 0 and c2 > 0`
- `c0` odd → `abs(c1 - c2) > 2`

The important interview skill is not memorizing the final condition, but reducing the game to residue counts first.

## Brute Force

### Idea

For a small number of stones, simulate every possible move recursively.

The state needs:

- Which stones remain.
- Current sum modulo 3.
- Whose turn it is.

For every possible move, recursively evaluate the resulting state.

### Complexity

With `n` stones, the number of possible move sequences can be exponential, roughly `O(n!)` without aggressive memoization.

With memoization over subsets, the state space is still exponential: `O(2^n * 3)`.

### Why it is inefficient

LeetCode's input can be much larger than what subset-state dynamic programming can handle. The key is to find a mathematical reduction instead of simulating the game.

## Optimal Solution

### Key observations

1. Replace every stone with `stone % 3`.
2. Count the three residue classes.
3. The exact values and positions of stones are irrelevant.
4. The game has only three possible sum remainders.
5. The parity of `c0` determines which winning condition applies.

### Data structures used

A fixed-size array:

`count = [c0, c1, c2]`

### Algorithm explanation

1. Iterate through `stones`.
2. Increment `count[stone % 3]`.
3. If `c0` is even, return whether both `c1` and `c2` are non-zero.
4. Otherwise, return whether `abs(c1 - c2) > 2`.

## Algorithm

1. Initialize three counters to zero.
2. For each stone, increment the counter corresponding to its remainder modulo 3.
3. Check whether the number of remainder-0 stones is even.
4. If it is even:
   - Alice wins if there is at least one remainder-1 stone and at least one remainder-2 stone.
5. If it is odd:
   - Alice wins if the absolute difference between the remainder-1 and remainder-2 counts is greater than 2.
6. Return the resulting Boolean value.

## Complexity

### Time Complexity

**O(n)**

Each stone is processed exactly once.

### Space Complexity

**O(1)**

Only three counters are maintained, regardless of `n`.

## Edge Cases

- A single stone:
  - `[1]` → `False`
  - `[2]` → `False`
  - `[3]` → `False`
- All stones are divisible by 3.
- `c0` is even but one of `c1` or `c2` is zero.
- `c0` is odd and `abs(c1 - c2)` is exactly 2.
- `c0` is odd and `abs(c1 - c2)` is exactly 3.
- Many stones with identical values.
- Large input where iterating through the array is required but storing additional state is unnecessary.

## Alternative Approaches

### Recursive game simulation

Useful for understanding the game and validating the mathematical solution on tiny inputs, but exponential.

### Dynamic programming over subsets

Can memoize game states for small `n`, making it practical as a correctness oracle for testing. It is still exponential and unsuitable for the actual constraints.

### Residue-count mathematical solution

This is the preferred solution because it reduces the problem to three counters and runs in linear time.

## Interview Discussion

### Follow-up: Why do the actual stone values not matter?

Because the losing condition is based on whether the cumulative sum is divisible by 3. Therefore only each value's remainder modulo 3 affects the state.

### Follow-up: Why is the solution O(1) extra space?

The input is compressed into exactly three residue counts.

### Follow-up: Could you simulate the game?

Yes, but that leads to an exponential state space. The intended solution recognizes the modulo-3 invariant and reduces the game mathematically.

### Follow-up: How would you verify the mathematical condition?

Build a brute-force minimax solver for small arrays and compare its output against the O(n) formula over exhaustive or random small test cases.

## Personal Takeaways

- Reduce game problems to the smallest state that affects future moves.
- When divisibility is involved, immediately inspect values modulo the divisor.
- Count equivalent states instead of treating identical residue classes as distinct.
- Before trusting a compact mathematical condition, validate it against a brute-force oracle on small inputs.
- A constant-space solution can still require substantial game-theoretic reasoning.
